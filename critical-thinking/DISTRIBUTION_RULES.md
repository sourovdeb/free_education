# Education Distribution Rules

Owner-requested destinations: `sourovdeb/free_education`, the owner's Gmail, and draft-only pages on `sourovdeb.com`.

These are saved workflow instructions for an authorized future run. They do not monitor future chats, install a scheduler, send recurring emails or guarantee access in a later session.

## Apply when the owner requests a new education deliverable

1. Read the actual source and current delivery manifest. Keep source claims separate from new teaching adaptations. Do not infer completion from a prior message.
2. Inspect the existing repository and website before creating content. Reuse an exact matching draft by stored ID. A similar title alone is not enough. Preserve published pages; do not edit or unpublish them to stage new work. Use an appropriate existing parent page.
3. Give each substantive creation a stable identifier and its own page or clearly identified resource entry. Do not turn every support file, old version or duplicate into another lesson.
4. Reserve a video section, recording prompt, transcript/captions section and post-video exercise. Leave the video URL empty until a real approved recording is supplied. Never fabricate a video, embed or transcript.
5. Explicitly set WordPress status to draft on every write. Never set publish, future or an automatic publication date. Avoid changes to live menus, widgets and reusable patterns.
6. Prepare a public-safe GitHub edition. Exclude personal records, unredacted screenshots, signed download links, credentials and unrelated material. Public branches and draft pull requests are still public.
7. Use a dedicated branch and draft pull request. Do not merge or enable automatic deployment without explicit owner approval. Preserve unrelated files and follow the repository's actual conventions where compatible.
8. Read back changed content. Check IDs, slugs, status, internal links, arithmetic, source fidelity and required sections. Report any failed or unperformed checks precisely. A prompt saying to verify is not verification.
9. Send one delivery email to the account owner after the current requested work is ready, using the resolved Gmail identity. Include actual repository and editor links, attachments where supported, and blockers. Do not email subscribers or other people without authorization.
10. Save a delivery record with source version, paths, WordPress IDs, returned statuses, Git commit/PR references, email outcome and exact next action. On a failed write, read the destination before retrying to avoid duplicates. Stop retrying permanent access failures.

## Before publication

The owner reviews content, sources, accessibility, downloads and video rights, then explicitly authorizes publication. Do not treat a resource saved to GitHub as permission to publish a website page. Do not claim that this file applies automatically to future sessions; it must be provided or retrieved in the relevant workflow.
